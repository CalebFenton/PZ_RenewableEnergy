# Developer notes

Commands, and Project Zomboid Build 42 behavior that the mod's code can't show you. Each game fact names its source in the decompiled 42.21.0 Java or the vanilla Lua, so you can check it again after a game update. Published modding docs mostly describe Build 41; when they disagree with the game files, trust the game files.

Add a command as one line: what it's for and how to run it. Add game behavior only if it fails silently or cost time to find. Leave out what a mode builds or shoots (its source file lists that), what a script's header or `--help` says, the mod's own code and numbers, and anything the harness docs already cover.

## Commands

The scripts in `dev/` are entry points into the shared test harness in `dev/harness`, a git submodule (run `git submodule update --init` after cloning), which `dev/harness.conf` configures for this mod. They run the game from its own cache under `$TMPDIR`, so they never touch your saves, settings or mod list. `dev/harness/docs/running.md` covers every flag, environment variable and console line, and `dev/harness/docs/debugging.md` which run answers which question. The tests, the debug scenario and the promo, art and loot code live in the dev mod `dev/RenewableEnergyDevHarness`, which is never published.

- `dev/static-check.sh`: run after every change. Compiles every Lua file with the game's compiler and cross-checks it against the installed game, plus this mod's tile and stash house checks in `dev/check` (`dev/harness/docs/static-check.md` lists the checks).
- `dev/validate-server.sh`: boots a dedicated server with only this mod and fails if the mod logs an error.
- `dev/run-debug-client.sh`: starts the debug client with the mod, the dev mod and the harness mod, at the main menu; see [Debugging by hand](#debugging-by-hand).
- `dev/run-debug-client.sh --test`: runs every test unattended and exits nonzero on a failure or any Lua error. Needs a JDK's `javac`. Narrow it with `TESTS=<prefix>,...`, `--changed` (by `TEST_MAP` in `dev/harness.conf`) or `--failed`.
- `dev/run-debug-client.sh --test --stay`: keeps the game open, and the next `--test --stay` reloads only the test files and reruns in it. Finish with a plain `--test`, since the kept world holds what earlier runs left.
- `dev/run-debug-client.sh --test --mp`: the same tests against a dedicated server; add `--stay` to keep both open. `dev/harness/docs/multiplayer.md` explains the server channel.
- `dev/run-debug-client.sh --loot`: measures how often each of the mod's items spawns in each loot list and room container, then, per town and for the whole map, the modules and watts and the batteries and watt-hours a thorough player finds, the world banks by room, and yardsticks to read them by: what a module banks a day in July and December, and what each appliance draws. Run it after changing loot or world spawns, and check the README's and the player guide's hints on what's rare still hold. `dev/loot/census.py` counts the towns and the map it uses; rerun that only after the map changes.
- `art/models/make.sh`: rebuilds every model, texture, icon and tile from `art/models/items.py`, `art/models/tiles.py` and `tools/make_tiles.py`, and writes review sheets and an `index.html` of every model, tile and icon, each named, to `$TMPDIR/renewable-energy-previews`. Its header says what each step writes and needs.
- `tools/pack_textures.py`: rebuilds `renewable_energy.pack`; `make.sh` runs it. `python3 dev/harness/check/tiledefs.py <file.tiles> all` prints every tile's properties.
- `dev/run-debug-client.sh --art`: renders every tile, overlay, item and trailer state to `<cache>/Screenshots` for review; `RenewableEnergyDevArt.lua` in the dev mod lists the shots.
- `TESTS=renewable_energy_world_arrow_board_lid_swings dev/run-debug-client.sh --test --mp`, then `dev/lid-shots.py`: shows what a multiplayer client draws of the battery box lid as it swings, which `--art` can't, since it runs single player only. Only a run whose `TESTS` is exactly that name takes the shots; the script's header says what the sheet shows.
- `dev/run-debug-client.sh --promo`, then `art/promo/compose.py`: shoots the README and Workshop art into `art/promo/captures`, then lays it out into `art/promo/images`, the Workshop gallery in `art/promo/gallery`, `42/poster.png` and `preview.png`. `RenewableEnergyDevPromo.lua` in the dev mod lists the setups and shots. Commit the captures, so a layout change needs only `compose.py`.
- `PROMO=<group>,... dev/run-debug-client.sh --promo`: reshoots only those groups (`MODE_GROUPS_promo` in `dev/harness.conf`) and replaces only their captures. Reshoot the group you are changing, then check `git status art/promo/captures`. There is no `--promo --stay`: a second run in the same world would find its places taken by what the first one built.
- `dev/review.sh`: lays out the images, renders the README to HTML and PDF, and zips the mod and the dev mods as players install them, without starting the game; `--art` adds the art review page. Its header says what it needs and where the files go.
- `dev/workshop-txt.sh`: writes `workshop.txt`'s description from `README.md`, leaving out the sections `WORKSHOP_SKIP` in `dev/harness.conf` names; the static check fails while the two differ.
- `dev/workshop-gallery.sh`: lists the Workshop item's gallery; `--upload` replaces its images with `art/promo/gallery`'s. Needs Google Chrome and the item published; the first run opens Chrome to log in to Steam.

`README.md` is the Workshop page, and `dev/harness/docs/workshop-page.md` says what goes on it. It links the images by relative path, and `workshop.txt` by raw URL, which shows nothing until the repository is public; a renamed image breaks the Workshop page.

## Debugging by hand

`dev/run-debug-client.sh` without flags gives you these. With `-debug` in the game's Steam launch options a normal game has the debug menu, but neither the scenario nor the tests, which come with the dev mod.

- The scenarios are under the **SCENARIOS** header in the middle of the main menu, which a game run with `-debug` shows collapsed (vanilla's `DebugUIs/DebugScenarios.lua`); hover over it to list them, and click one to start it. **Renewable Energy** starts a zombie-free world with a character who knows every recipe.
- **Renewable Energy QA** is for playing the mod through by hand: by a barn, a character in god mode and invisible, who carries anything and has every skill and recipe of the mod, holds two toolboxes with the small tools the recipes and menu jobs take, and finds laid out on the ground, a group of rows for each of the mod's systems, one of every item of the mod, enough of every other input to make each recipe once, what the menu jobs take, the crafting stations, a treadmill and the arrow board trailer.
- To run one test, open the debug menu with the bug icon, then **Dev**, **Unit Tests**, **Timed Actions**.
- To see the loot of vanilla lists, right-click the world and choose **UI**, then **Generate Loot UI**.
- Restart the client after changing Lua. `reloadLuaFile()`, which the debug Lua file browser uses, runs the file again but ignores its `Events.*.Add` calls (`LuaCompiler.rewriteEvents`), so the old handlers keep running.
- A dedicated server has no `-debug` argument; it reads only the JVM property `-Ddebug`.
- In debug mode a Lua error stops the game in the error handler, even inside `pcall`.
- In debug mode, vanilla logs errors about fonts, `FluidContainerScript` names, a mannequin zone, missing tiles, and missing icons. None come from this mod.
- `getCore():TakeFullScreenshot("name.png")` writes to `<cachedir>/Screenshots/` without macOS Screen Recording permission.

## Writing tests

The harness docs (`dev/harness/docs/`) cover the runner, the fixtures and the server channel; this section has only the game's side.

- `player:setTimedActionInstantCheat(true)` (allowed for everyone in debug mode) makes every action that asks `isTimedActionInstant()` in its duration take one tick, crafting, research, reading and the moveables cursor included. `perform()` and `complete()` still run, so a craft uses its inputs, makes its outputs, runs `OnCreate` and gives XP. Walking isn't shortened. The debug option **Cheats > Timed Action > Instant** does the same for every character (`IsoGameCharacter.isTimedActionInstant`), so a test that measures a duration must fail while it is on.
- `getGameTime():setTimeOfDay(t)` moves `getWorldAgeHours()` with it, backwards too. On the next tick `EveryOneMinute` fires once, and `EveryTenMinutes` once if the minute of the hour lands in another ten; `EveryHours` doesn't fire, because `GameTime.update` only compares the hour before and after its own step.
- `getGameTime():setMultiplier(n)` speeds up the clock and every timed action alike (`GameTime.getMultiplier`). It drops back to 1 when the character moves without a path or a zombie comes close (`IsoPlayer`).
- `ISInventoryPaneContextMenu.OnNewCraft` crafts through the same path as a right-click, and when the game refuses, it queues nothing and says nothing. `HandcraftLogic` can tell you why.
- A table for an `AnySurfaceCraft` recipe must come from `IsoObject.new(square, spriteName, name)`. `IsoObject.new(square, spriteName)` builds a new sprite from the texture alone, so the object looks like a table but has no `Surface`. `findCraftSurface` also skips squares the character can't reach, such as the far side of a wall.
- `getScriptManager():getCraftRecipe(name)` and `instanceItem` return nil for a name that doesn't resolve; check before you index the result.
- A vehicle spawned this frame joins `IsoCell.vehicles` only on the next cell update, so wait for it before looking for it.
- `IsoCell.getVehicles()` is a Java `Set`, which Lua can neither index nor walk. Find vehicles through the squares they stand on, with `square:getVehicleContainer()`.
- A hard knock on a hitched pair, such as a crash, snaps the hitch unless it was made in the last two seconds (`Bullet.onVehicleConstraintImpulse`), so a test that pushes a hitched pair keeps it on open ground rather than relying on how soon the knock comes.
- `teleportTo` a square that isn't loaded, called from a timed action's `update`, doesn't stick: the character stays put. Teleport from an `Events.OnTick` handler and keep a `RenewableEnergyTest.waitUntil` on the queue until it is done.
- A vehicle a test removed can come back, with its key, when a later test unloads its chunk and loads it again straight away: seen in about half of a session's runs with a car removed one test before a chunk-reload trip. Staying away two seconds before going back stopped it (`T.awayAndBack`); the cause wasn't pinned down, and the game hot-saves loaded chunks every second (`IsoChunkMap.hotSaveFrequency`).
- `tooDarkToRead()` is false while either hand holds a lit light, or an attached item emits one (`IsoPlayer.tooDarkToRead`); otherwise it reads the square's light level, so indoors the tests' daylight hour can still be too dark for a job that needs light. `T.holdLight` puts a lit flashlight in the off hand.

## Ground truth

The game ships its Lua, scripts, and assets unpacked, and its Java decompiles cleanly. The bundled Java has no `jar` tool, so `unzip` and `zip` pick out the `zombie` packages:

```sh
PZC="$HOME/Library/Application Support/Steam/steamapps/common/ProjectZomboid/Project Zomboid.app/Contents"
cat ~/Zomboid/version.txt                     # installed version, such as 42.21.0 4a0e9546ec
ln -sfn "$PZC/Java/media" /tmp/pzmedia        # vanilla lua/, scripts/generated/, clothing/, models_X/
mkdir -p /tmp/pztools /tmp/pzclasses /tmp/pzsrc && cd /tmp/pzclasses
curl -sSL -o /tmp/pztools/vineflower.jar https://repo1.maven.org/maven2/org/vineflower/vineflower/1.11.1/vineflower-1.11.1.jar
unzip -q "$PZC/Java/projectzomboid.jar" 'zombie/*' && zip -qr /tmp/pztools/zombie.jar zombie
"$PZC/PlugIns/jre-aarch64/Contents/Home/bin/java" -jar /tmp/pztools/vineflower.jar -dgs=1 -thr=8 -log=WARN \
    "-e=$PZC/Java/projectzomboid.jar" /tmp/pztools/zombie.jar /tmp/pzsrc
```

Start from these files:

- Lua globals are the `@LuaMethod(name = ...)` methods in `zombie/Lua/LuaManager.java`; exposed classes are its `setExposed(X.class)` calls.
- `zombie/Lua/LuaEventManager.java` lists the Lua events. Search for `triggerEvent("Name"` in both the Java and the vanilla Lua to see which side fires each one.
- Script keys are parsed in `zombie/scripting/objects/Item.java` (`DoParam`) and in `CraftRecipe.java`, `InputScript.java`, and `OutputScript.java` under `zombie/scripting/entity/components/crafting/`.
- Vanilla patterns are in `/tmp/pzmedia/lua/shared/TimedActions/` and `/tmp/pzmedia/scripts/generated/`.
- Subscribed Workshop mods, some already ported to Build 42, are in `~/Library/Application Support/Steam/steamapps/workshop/content/108600/`.

## Mod layout and loading

Build 42 lists a mod folder only if it has `common/mod.info` or `<version folder>/mod.info`, and ignores files at the mod root.

- The game uses the child folder with the highest numeric name that is at least 42.0 and at most the game version, comparing major × 1000 + minor and ignoring the patch number. A folder named `42` works for every 42.x release.
- `common/media` loads first, and the version folder overrides files at the same relative path. A mod Lua file at the same relative path as a vanilla file replaces the vanilla file, so keep every Lua file under a `RenewableEnergy` folder. Texture, model and pack sprite names are just as global across mods, so give every one of them the mod's name.
- `tiledef=<file> <number>` gives the tiledef file a number from 100 to 8189 (`ChooseGameInfo`). The number alone decides the tiles' sprite ids, `1048576 + (number - 2) × 262144 + (tileset - 1) × 512 + tile` (`IsoWorld.getSpriteID`), and vanilla uses 1 to 8, so two mods' tiles share ids only if the mods pick the same number.
- `versionMin` and `versionMax` in `mod.info` are the only compatibility check (`ChooseGameInfo.Mod.isAvailableSelf`). The mod list shows them as `min - max`, in red when the game is outside the range, and the game doesn't load such a mod. The "unsupported mods" filter only hides mods made for versions before 42.0 (`Core.getBreakModGameVersion()`).
- With Steam running, the game finds mods in `~/Zomboid/mods/*`, in Workshop staging folders (`~/Zomboid/Workshop/*/Contents/mods/*`), and in subscriptions. With `-nosteam` it reads only `<cachedir>/mods`. Two copies with the same `id` conflict, so unsubscribe from the Workshop copy while you develop.
- Leaving a game re-initializes Lua (`IngameState.exit()` calls `LuaManager.init()`), so module-level Lua state starts fresh for every loaded game.

## Scripts

Item and recipe scripts are in `media/scripts/*.txt`. Only `/* */` comments work in them; `//` and `--` don't.

- Set `ItemType = base:normal` (or `base:drainable`, `base:moveable`, and so on). The Build 41 key `Type = Normal` becomes an unknown parameter, and the item has no class.
- An unknown item parameter is copied into every new item's modData (`Item.DoParam`, `defaultModData`), with a `DetailedInfo` warning.
- A `base:moveable` item needs an `Icon`. The inventory draws the tile it places, but the crafting window draws the script item's icon, which is nil without one: an empty square, and `ISCraftInventoryPanel` throws when it lists the item as a possible input. Vanilla gives every moveable an `Icon`.
- Every item that a recipe outputs can be researched for that recipe (`OutputMapper`), and nothing else is offered unless the item lists `ResearchableRecipes`. Research needs two thirds of the recipe's highest skill level (`CraftRecipe.getResearchSkillLevel`).
- A heavy item dropped on the floor, as `Actions.addOrDropItem` does when a craft's output doesn't fit (the main inventory holds 50), turns into an `IsoGenerator` if the item has the `base:generator` tag and a `WorldObjectSprite` (`IsoGridSquare.AddWorldInventoryItem`).
- `ItemName.json` (key `Module.Item`) overwrites `DisplayName`, and vanilla items have no `DisplayName`.
- A bare name resolves only in `module Base` (`ScriptBucketCollection.getScript`): a model in `WorldStaticModel`, and a recipe in `getCraftRecipe(name)`. The game looks recipes up by bare name when researching an item and in the magazine's recipe list, so craftRecipes go in `module Base`, with a prefix against name clashes.
- The item `OnCreate = Some.Lua.func` calls `func(item)` on every instantiation: loot, crafting outputs, debug spawns, loading a save, and a multiplayer client receiving the item. When loading, `item:load()` then replaces the modData, but only if the saved modData isn't empty, so always write at least one key. Uses set on a drainable item in OnCreate are overwritten afterwards.

### craftRecipe

Build 41 `recipe` blocks no longer load.

- Lines without `=`, such as the Build 41 `Time:30`, are skipped without an error. Unknown keys log an error, and throw in debug mode.
- Input flags in `flags[...]` are case-sensitive enum names, and `[...]` lists must not contain spaces. `NoBrokenItems` has no effect; broken items are always refused unless an input sets `AllowDestroyedItem`.
- Use `tags[base:screwdriver]` for tool tags and `mode:keep` for tools. An input line can list items and tags together, `[Base.Glasses_Reading] tags[base:magnifier]`, and accepts any of them (`InputScript.OnPostWorldDictionaryInit`).
- An input of a drainable item counts uses: `item 1 [Base.Glue]` takes one of the tube's five uses. Part-used items add up, so two tubes with one use each pay `item 2 [Base.Glue]` (`CraftRecipeData.consumeInputFromItems`); on a scaled line such as `item 1 [Base.Epoxy;2:Base.Glue]`, vanilla still takes only one use of the scaled item (`CraftRecipeData.processDestroyAndUsedItems` caps it at the unscaled amount). Scaled the other way, `item 2 [Base.Glue;1:Base.Epoxy]` takes one use of epoxy but won't start on a tube with only one left: `consumeInputFromItems` credits a scaled item no more uses than it has. So no single line takes 2 glue or 1 epoxy exactly; vanilla gives each its own recipe (`FixWithGlue`, `FixWithEpoxy`). `flags[ItemCount]` takes whole items instead.
- `MetaRecipe = <name>` makes a recipe known whenever `<name>` is in the character's known recipes (`IsoGameCharacter.isRecipeKnown`), so a twin recipe is taught by whatever teaches the other, in older saves too. In debug mode, a `NeedToBeLearn` recipe with neither an AutoLearn nor a magazine that teaches it by name is logged at world load as learnable only by research, or not at all (`ScriptManager.VerifyAllCraftRecipesAreLearnable`), MetaRecipe or not.
- Worn items count as inputs, and a worn `mode:keep` tool stays worn. `flags[IsNotWorn]` refuses worn and equipped items.
- Input lines take distinct items, line by line in the order they are listed: a line skips items an earlier line took (`CraftRecipeData.consumeInputFromItems`). So `item 2 [A]` followed by `item 1 [A;B]` takes three A, or two A and a B.
- `Tags = AnySurfaceCraft` needs a table or counter within 3 tiles (`HandcraftLogic`), and the craft walks the character to it. A tag other than `InHandCraft`, `AnySurfaceCraft`, `EntityRecipe`, and `Outdoors`, on a recipe without one of them, makes it need a crafting bench entity (`CraftRecipe.requiresSpecificWorkstation`). The `Electrical` tag does nothing else; `category = Electrical` sets the crafting window category.
- Every recipe needs light unless it has the `CanBeDoneInDark` tag (`CraftRecipeData`, `IsoPlayer.tooDarkToRead`).
- When the server refuses a craft at perform (a skill short, the recipe unknown, a container out of reach: `CraftRecipeManager.isValidRecipeForCharacter`, `HandcraftLogic.performCurrentRecipe`), it drops the craft without a word, and `ISHandcraftAction:complete` still returns true, so the client's action ends as if it had crafted.
- `xpAward = Electricity:10` and `SkillRequired = Electricity:2` replace Build 41 `OnGiveXP` and `SkillRequired:`. The global `addXp(player, perk, amount)` gives what an `xpAward` gives (`CraftRecipe.addXP`), multipliers included, only without the halo text, so OnCreate can award XP that depends on the inputs. None of vanilla's kiln recipes has an `xpAward`.
- `OnCreate(craftRecipeData, character)` runs once, locally in single player and on the server in multiplayer, after the outputs were sent to the client. Call `result:syncItemFields()` after changing an output.
- `OnTest(item, character)` runs for every candidate input item, tools included.
- `OnTest` and `OnCreate` accept dotted Lua paths (`LuaManager.getFunctionObject`). `OnAddToMenu(params)` must be a plain global name, because the crafting window reads it with a raw `_G` lookup.
- `craftRecipeData:getAllConsumedItems()` excludes `mode:keep` inputs, and `getFirstCreatedItem()` returns the output. No flag copies modData to the output, and vanilla adds per-input counter keys to the output's modData after OnCreate.
- Recipes can't be switched on and off at runtime. To gate one with a sandbox option, use OnTest, which blocks crafting on the server too, and OnAddToMenu, which hides the recipe.
- `CraftRecipe:clearRequiredSkills()` and `addRequiredSkill(perk, level)` change a recipe's skill requirement in place, and the can-craft check, craft time, and every crafting window read that list. Single player, the server, and each client hold their own recipe objects, rebuilt from the scripts whenever Lua reloads, so apply the change on every side. No event fires when an admin changes sandbox options mid-game (`GameServer.receiveSandboxOptions`).
- Build 41 `fixing` blocks still parse, but only with `=`: `Require = ...`, `Fixer = ...`.

### Sandbox options

`media/sandbox-options.txt` must start with `VERSION = 1,`. Option types are `boolean`, `integer`, `double`, `enum`, and `string`. The translation keys are `Sandbox_<translation>` and `Sandbox_<translation>_tooltip` for an option, `Sandbox_<valueTranslation>_option<N>` for enum values numbered from 1, and `Sandbox_<page>` for the page title.

`valueTranslation` is read only for `enum` options (`SandboxOptions.java`, `CustomEnumSandboxOption`).

`SandboxVars.<Table>.<Key>` holds every option of every active mod as soon as Lua loads (`shared/Sandbox/SandboxVars.lua` calls `initSandboxVars()`), and the setters reject values outside `min` and `max` (`DoubleConfigOption.setValue`). Read options without Lua defaults, which would hide a misspelled option name.

## Translations

The game loads only JSON translations, from `media/lua/shared/Translate/<LANG>/<File>.json`, and ignores `.txt` translation files.

- File names that load include `ItemName`, `Recipes`, `IG_UI`, `Tooltip`, `ContextMenu`, `Sandbox`, and `UI` (`Translator.java`).
- Item keys are `"Module.Item"`, and craftRecipe keys are the bare recipe name. Prefixed keys go in the matching file: `IGUI_` keys in `IG_UI.json`, `Tooltip_` keys in `Tooltip.json`.
- Debug builds parse strict JSON, without comments or trailing commas. Write `%%` for a literal percent sign.
- Vanilla keys such as `ContextMenu_Turn_On`, `ContextMenu_AddBattery`, and `ContextMenu_Remove_Battery` are already translated into every language.
- An entity style's `DisplayName` (a `xuiSkin` entry) is looked up, spaces removed, among the recipe names (`Recipes.json`) when the scripts load, and what comes of that goes through `getText` whenever the name is shown (`XuiSkinScript`, `XuiSkin.EntityUiStyle.getDisplayName`). A debug dedicated server logs a missing translation for every entity's name and, since it loads no textures, "Could not find icon" for every style's `Icon`, vanilla's included, so `SERVER_IGNORE` in `dev/harness.conf` skips ours.
- The game's Lua compiler keeps a source string one byte per character and then decodes it as UTF-8 (Kahlua `LexState.save`, `newstring`), so a non-ASCII character in a Lua literal, such as `°` or `³`, shows as `?`. JSON translations load as UTF-8 and keep them; take such text from a translation, or from Java (`Temperature.getTemperaturePostfix`).

## Lua runtime

### Who runs what

| Context | `isClient()` | `isServer()` | Lua that runs |
|---|---|---|---|
| Single player | false | false | Client, shared, and server Lua in one state |
| Multiplayer client | true | false | Client, shared, and server Lua; guard server handlers with `isClient()` |
| Dedicated server | false | true | Shared and server Lua; client Lua is only checksummed |

- Server Lua loads after client Lua, so client Lua can't `require` a server file at load time. It has to require it at runtime, when `require` hands back the loaded file's table.
- `getVehicleById` returns nil in single player, because vehicles are registered with `VehicleManager` only on a server (`BaseVehicle.createPhysics`). Find a vehicle through the squares it stands on instead.
- The game's Lua has no `next`: a call fails with "tried to call nil". Count a table with `#` or a loop over `pairs` instead.
- `getScriptManager():getAllBuildableRecipes()` lists the build menu's entity recipes, which `getAllCraftRecipes()` leaves out (`ScriptManager.java`).
- A built entity's `SpriteConfig` accepts only the tiles of its own entity's faces, and each tile belongs to one entity. When an object loads (each multiplayer client receiving it, each chunk load from the save) with a tile its SpriteConfig doesn't name, the game logs "Invalid SpriteConfig object!" and keeps the component without its tile info (`SpriteConfig.initObjectInfo`); `getMasterObject()` is then nil for it, and an entity created on such a tile gets only its SpriteConfig (`GameEntityFactory.instanceComponents`). An object that changes tile changes entity too: `RenewableEnergy.setEntityTile` replaces its components with the new tile's entity, found as vanilla's `MORainCollectorBarrel` finds one (`SpriteConfigManager.getObjectInfoFromSprite`), and a server then sends them on with `sendSyncEntity`, which a client applies only to an object it has registered as an entity (`GameEntityNetwork.parse`).
- `IsoPlayer.tooDarkToRead()` is false for any player that isn't local (`IsoPlayer.java:8605`), so a server can't refuse a remote player's job for the dark; that rule belongs in the client's menu and `isValid()`.

### State and syncing

- `item:syncItemFields()` sends an item's modData, uses, and condition to the other side: from the server to the player whose inventory holds it, or from a client to the server. The global `syncItemFields(player, item)` does the same for that player. Both do nothing in single player.
- On the server, `Actions.addOrDropItem(character, item)` adds and syncs an item. To remove one, call `container:Remove(item)` and then `sendRemoveItemFromContainer(container, item)`; the send does nothing outside the server.
- A client sends its whole player modData to the server (`transmitModData`), and the server replaces its copy with it. ISHotbar does this after every clothing change, so anything the server writes to player modData can disappear.
- The Global Object System (`zombie/globalObjects`) saves the modData keys an object system names with `setObjectModDataKeys` with the world, even while the object's chunk is unloaded. Loading puts back every key the save holds, named or not (`SGlobalObject.load`), so a key dropped from the list stays in old saves until the mod clears it. `setObjectSyncKeys` sends the keys it names to every client, in single player too: each `updateOnClient`, like the system's `sendCommand`, goes to every connection however far away (`SGlobalObjectNetwork.sendPacket`). A client copies the keys it gets onto its copy and keeps any key the update left out (`CGlobalObjectSystem.receiveUpdateLuaObjectAt`), so a value that can become nil belongs inside a synced table. To reach one player, the server calls the global `sendServerCommand(player, module, command, args)`, which does nothing in single player.
- A system registered with `SGlobalObjects.registerSystem` must put a `getInitialStateForClient` function in its modData, or the game throws when a client connects (`SGlobalObjectSystem.getInitialStateForClient`). `SGlobalObjectSystem.lua` defines one for the systems derived from it.
- A container's `AcceptItemFunction` filter is not saved with the container. Set it again whenever the object loads (`MapObjects.OnLoadWithSprite`) and whenever it is placed (`OnObjectAdded`), on every side. `sendObjectChange(IsoObjectChange.CONTAINERS)`, which a container's new capacity needs to reach clients, replaces the clients' container objects and so drops their filters too (`IsoObject.loadChange`).
- `MapObjects.OnLoadWithSprite` keeps one function per sprite and priority: a second registration replaces the first without a word (`MapObjects.java`). Single player loads the client and server folders into one state, so a client and a server handler for the same sprite need different priorities.
- On a server the global `sendItemStats(item)` sends the item to the clients near its container's square, object or player, and to every client when the container has none, which throws while it writes the container's place (`GameServer.sendItemStats`). Only scratch containers that never enter the world, as tests and loot measurements make, have none.
- A battery's charge is stored as whole uses of its `UseDelta` (`InventoryItem.setCurrentUsesFloat` rounds) and read back as a 32-bit float, so a charge read back after it is set is off by up to half a use: 0.80 on a car battery reads 0.79999995. Compare charges in whole uses, `getCurrentUses()` against `getMaxUses()`, which is `floor(1 / UseDelta)` (`DrainableComboItem`).
- Picking an object up or scrapping it needs its containers empty (`isObjectNoContainerOrEmpty`, `ISMoveableSpriteProps`); a sledgehammer dumps them onto the floor first (`ISDestroyStuffAction.complete`, `dumpContentsInSquare`) and only then removes the object, so `OnObjectAboutToBeRemoved` finds the container already empty. Picking up a plain `IsoObject` keeps only its modData's `movableData` on the item; an `IsoThumpable` keeps all of it.
- The noxious smell moodle and the food sickness from corpses come from a count per chunk level, split by building (`CorpseCount`), which only `IsoDeadBody.addToWorld` and `removeFromWorld` change, and neither needs the body on a square: a body made with `IsoDeadBody.new(getCell())`, moved with `setX`, `setY` and `setZ` and added to the world counts without being drawn, looted, rotted or saved. A chunk zeroes its counts when it unloads, with no event, and again just before `LoadChunk` fires (`IsoChunk.doLoadGridsquare`), and an outdoor count goes below zero if a body is removed after that (`CorpseCount.ChunkLevelData.corpseRemoved`). A multiplayer client's moodle follows the rate the server sends every two seconds (`PlayerDamagePacket`, `NetworkPlayerManager`).
- A character smells the corpse count of the 3 by 3 chunks (8 squares each, `DIM`) around its own, on its level, outdoors or in its building, plus live zombies within 12 squares when the zombie health option is on (`CorpseCount.getCorpseCount`). Distance within that block counts for nothing: a pile smells the same anywhere in it and not at all a square past it, so a smell that fades must spread its count over neighbouring chunks.

### Timed actions in multiplayer

- If an action class has `complete()`, the client runs `start()`, `update()`, and `perform()`, and the server runs `complete()`. Single player runs `perform()` and then `complete()` in the same tick (`IsoGameCharacter`'s action loop).
- The server rebuilds the action by calling `<Class>:new()` with the values of the fields named like `new()`'s parameters, in parameter order (`NetTimedAction`), each sent by its type at run time (`PZNetKahluaTableImpl.save`), so one parameter can carry an `InventoryItem` or an `IsoObject`. Parameter names must equal field names, and every argument must be serializable. Items are sent as container plus id, so they must be in a container. An unsupported argument type is dropped and shifts the arguments after it.
- The server never calls `isValid()`, `update()`, or `perform()`, so check the action again in `complete()`; returning `false` rejects it.
- The server times an action in real time, at 20 ms per tick of its `getDuration()` (`NetTimedAction.getDuration`), whatever the frame rate or the game speed. Vanilla's mechanics cheat (`setMechanicsCheat`) makes a vehicle part's install and uninstall take one tick and skips their `isValid`.
- On the client, fetch items again by id in `start()`, as vanilla does, because server syncs can replace the item objects.
- Until the server's answer that the action is done arrives, the client checks `isValid()` every tick, and the item syncs `complete()` sends (`sendRemoveItemFromContainer`, a used fixer) can arrive first. An `isValid()` that checks for an item the action used then fails, so the client calls `stop()` instead of `perform()`, and `ISBaseTimedAction.stop` empties the whole queue; what the server did stands. Vanilla's `ISInstallVehiclePart` stops checking once its job delta reaches 0.9, which an instant action never does, and `ISFixVehiclePartAction` always checks, so welding with the last sheet metal ends that way.
- Single player and the client call `isValid()` every tick, before `waitToStart()` and every `update()` (`IsoGameCharacter`'s action loop, through `LuaTimedActionNew.valid`), so a check that walks the inventory or a list of objects belongs in `start()` and `complete()` instead. A `forceStop()` in `start()` stops the action in that same tick and empties the queue, as `ISHandcraftAction.start` does when the inputs picked by hand can't make the recipe. `isValidStart()` is no substitute: the queue asks it only of an action that follows another (`ISTimedActionQueue.onCompleted`).

### Generators

The mod's battery banks are `IsoGenerator`s, so all of this applies to them.

- `setActivated` is not a plain setter: it plays the start or stop sound (prefixed by the tile's `GeneratorSound` property, else `Generator`), updates every fridge in range, sets the building's toxicity, and syncs. Measure the load with `setSurroundingElectricity()` and `getTotalPowerUsing()`, which work whether or not the generator runs.
- `getTotalPowerUsing()` is multiplied by the GeneratorFuelConsumption sandbox option (default 0.1).
- Toxicity belongs to the whole building, and gas generators set it when they start and once an in-game hour after. Restore only what your own `setActivated` changed.
- Squares stay powered after a running generator is removed, until `setSurroundingElectricity()` runs on it switched off (`IsoChunk.isGeneratorPoweringSquare`). Switch it off before it leaves the square.
- `IsoGenerator.isPoweringSquare` reads static copies of the GeneratorTileRange and GeneratorVerticalPowerRange options that only constructing a generator sets (`IsoGenerator.java:107-113`), so before the first generator, or after the options change, they are stale; read `SandboxVars` instead.
- `IsoGenerator.update()` is what acts on `chunkLoaded`'s request to repower squares in newly loaded chunks; a generator taken out of the cell's process list has to call `setSurroundingElectricity()` itself.
- Every running generator bills itself for every powered appliance in its reach, whatever else reaches it (`setSurroundingElectricity`). `setTotalPowerUsing` sticks only until that rebuilds the bill, which any appliance switching in reach (`IsoGenerator.updateGenerator`) or chunk loading nearby (`chunkLoaded`) sets off; `update()` burns the bill at the hour, before it rebuilds. Both only flag the generator, and its next `update()` rebuilds. A dedicated server runs its world updates ten times a second and serves client commands in between (`GameServer.main`), so a command answered soon after the flag still reads the old bill, however many ticks the client counted.
- A generator dropped from the hands (`IsoGridSquare.AddWorldInventoryItem`) fires no Lua event. A player starting one runs `ISActivateGenerator:complete`.
- `setConnected`, `setCondition` and `setFuel` sync on the server. Call them after `transmitCompleteItemToClients()`, because a sync names the object by its index on the square.
- An overlay changed with `addAttachedAnimSpriteByName` reaches clients only through `transmitUpdatedSpriteToClients()`.
- Vanilla's generator context menu shows on any `IsoGenerator`, so hide it on banks: its **Take Generator** would hand back a `Base.Generator`.

### UI

- To add inventory context menu options, handle `Events.OnFillInventoryObjectContextMenu(playerNum, context, items)` and pass `items` through `ISInventoryPane.getActualItems(items)`, which unpacks stacks.
- `ISToolTipInv` also shows things that aren't items, such as fluid containers and energy resources. Check `instanceof(x, "InventoryItem")` before calling item methods.
- Vanilla explains a greyed-out option two ways. An option held back by one state or one tool says so in a plain sentence, as the generator's Plug In and Fix do (`ISWorldObjectContextMenu`, `ContextMenu_GeneratorFixTT`). An option that takes several things lists them all under "Needs" (`Tooltip_craft_Needs`) as `have/need`, in the good colour when met and the bad colour when short, and greys out while any is short: fixing an item (`ISInventoryPaneContextMenu.addFixerSubOption`), the build menu (`ISEntityBuildMenu`) and the mechanics window (`ISVehicleMechanics.doMenuTooltip`).
- In debug mode vanilla adds its debug options to every world context menu (`ISContextMenu:addDebugOption`) unless the debug option `UI.HideDebugContextMenuOptions` is on, which `getDebugOptions():setBoolean` sets.
- `addToUIManager` adds an element only at the next UI update (`UIManager.AddUI`), and `isReallyVisible()` stays false until then. Vanilla's radial menus toggle on it, so a hook run after `ISVehicleMenu.showRadialMenuOutside` can tell whether the call built the menu only from what the menu was before it.

### Vehicles

- A vehicle part's `model` blocks are drawn in the body model's frame: at a part model offset of zero, a mesh exported in the body's coordinates sits in place (`BaseVehicle` render transforms multiply the part's transform onto the body model's offset). A part model with a vehicle shader draws with the body's skin, mask, rust, damage and blood, so it can share the body's atlas.
- A part's models show while it holds an item and hide when it doesn't (`VehiclePart.setInventoryItem`), unless the part sets `setAllModelsVisible = false`; then only `part:setModelVisible(id, visible)` shows them. Showing a shown model, or hiding a hidden one, does nothing; any real change rebuilds the vehicle's model and, on the server, sends the vehicle's whole list of shown models to every client (`VehiclePartModels`), so a model a client hides on its own comes back unless the server hides it too. The list of shown models isn't saved, so set it again in the part's `init`.
- A part model moves only if its model script sets `static = false` (the default is true): only then does it get an animation player of its own (`BaseVehicle.ModelInfo.getAnimationPlayer`), and `vehicle:playPartAnim(part, id)` plays the clip that the part's `anim <id>` block names, at its `rate`, backwards with `reverse = true`, or held on its first frame (its last, reversed) with `animate = false`. Vanilla's door clips run from open to shut. While no clip plays, the game holds the door's `Opened` or `Closed` anim by its state (`BaseVehicle.updateAnimationPlayer`), but a held clip never ends, so a door that changes in another game keeps its old pose here until something plays a new anim. Vanilla plays a door's swing only in the game of the player who opens or closes it, as the action starts (`ISOpenVehicleDoor:start`). A swing takes the same real time at any frame rate, scaled by the game speed. `anim` blocks in a vehicle script add to a template's blocks of the same id (`VehicleScript.LoadAnim`), so a template's `sound` stays.
- A skinned FBX part mesh takes its bones from under the node named `VehicleSkeleton`, as vanilla names its vehicle meshes' armature, or else from the file's root node, and the game reads its clips' keys as written; only a file with a `Dummy01` node is read as a character, its keys scaled by 0.01 and turned (`ImportedSkeleton`). The game poses the bones by the clip's keys alone, a node without keys standing untransformed, and then draws the mesh through its own node's transform as well. Blender's FBX export keys the armature object too, with the turn to the file's axes, so an armature that carries that turn turns the mesh twice and puts it out of sight: leave the armature and the mesh untransformed in the file, with the data already turned. A clip named `Armature|Clip` in the file is `Clip` in the game.
- Nothing reports a part's condition changing: `OnVehicleDamageTexture` fires only when it crosses 60 or 40 with a driver in the vehicle or its tow, passes the driver, and fires before the condition is stored (`VehiclePart.setCondition`), and part `update` Lua runs only while the engine runs or the mechanics window is open. A look that follows condition has to be set wherever the mod changes it and checked again now and then.
- A part's `create` Lua runs once, when the vehicle first enters the world (`BaseVehicle.createPhysics` calls `createParts` only while the vehicle isn't `created`); a part added to the script later is never created on vehicles already in a save. Its `init` Lua runs on every load, on every side, and again on `VehiclePart.repair()`; its `update` Lua only on the authority, at most once a game minute (`VehicleParts.update`).
- A `part Name*` pattern in a vehicle script reaches only parts already declared above it (`VehicleScript.Load`).
- A whole-vehicle `template = Name` line copies all of the template, and also clears the vehicle's `physics` shapes and sets `useChassisPhysicsCollision` to the template's, which is true for a template without them (`VehicleScript.LoadTemplate`, `copyPhysicsFrom`). That leaves the vehicle with only its chassis box. To take just a part, write `template = Name/part/PartId`.
- A crash damages a vehicle, and through `BaseVehicle.crash` the vehicle it tows, only through vanilla part ids (`addDamageFront`, `addDamageRear`) and the front and rear end durability, which Lua can't read: `getVehicleInfo` throws on a vehicle without a `GasTank` part, and reflection works only in debug. In multiplayer the driver's client detects collisions and sends a `vehicle crash` command, and the server drops one for a trailer because it checks for a driver (`VehicleCommands.lua`). `getLinearVelocity(Vector3f)` reads a vehicle's velocity where its physics run: single player, or the client of the driver it is towed by.
- Crashes and character hits damage a part only while it holds an item, and a part's condition shows on the mask only for vanilla's ids: `EngineDoor` on Head and the front guards, `TruckBed` on Tail and the rear guards, `TrunkDoor` on Boot, doors and windows on theirs (`BaseVehicle.doDamageOverlay`). Only Hood, Boot, doors, windows and, under a `TrunkDoor` with `hasLightsRear`, the tail lamps turn dark grey when their part is empty. A part's `itemType` gets the vehicle's `mechanicType` appended (`Base.EngineDoor` becomes `Base.EngineDoor1`) unless the part sets `specificItem = false`, and `category = nodisplay` keeps it out of the mechanics window (`ISVehicleMechanics`), which otherwise names parts by id alone (`IGUI_VehiclePart<Id>`) whatever the vehicle.
- A vehicle with an `EngineDoor` part sends a character opening the mechanics window to that part's area first, and opens the hood only if the part has a door (`ISVehicleMenu.onMechanic`). Washing blood off offers each side whose area the script has, by name: Front `Engine`, Rear `TruckBed`, Left `SeatLeft` or `SeatFrontLeft`, Right `SeatRight` or `SeatFrontRight` (`ISWashVehicle`); a seat area seats no one unless a `passenger` names it.
- A vehicle's colour is rolled once, when it spawns, and `forcedColor = hue saturation value` in its script only applies then (`BaseVehicle.doVehicleColor`); `setColorHSV` changes it later.
- A part's install and uninstall `skills` (`Mechanics:2;Electricity:1`, split on `;`) never refuse: vanilla's tests leave `VehicleUtils.testPerks` commented out, and a skill below the part's only lowers the odds of success (`VehicleUtils.calculateInstallationSuccess`). The odds come from the `install` table's skills, for uninstalling too (`ISUninstallVehiclePart.complete`), and the Mechanics XP from the `uninstall` table's (`IsoPlayer.addMechanicsItem`). The mechanics window's tooltip lists them as "Recommended skill" in its good colour at any level, then the odds when they are short (`ISVehicleMechanics.doMenuTooltip`), and a failed job takes 5 to 10 condition off the item (`ISInstallVehiclePart.complete`). Vanilla lists a level it requires, such as taking engine parts', under "Needs" as `have/need`, in `ISVehicleMechanics.bhs` when short and `ghs` when met.
- A part with several models swings, and holds open or shut, whichever of them was shown first (`BaseVehicle.getModelInfoForPart`), and a static one gets no animation player, so a second model on a hinged part draws unmoved.
- Without its key, a locked trunk opens from a seat, through its own open, broken or missing window (`BaseVehicle.canUnlockDoor`), or by unbolting the lid in the mechanics window, which a locked door doesn't stop; only `mechanicRequireKey` does, until any door or window is open, unlocked or gone (`VehicleUtils.RequiredKeyNotFound`). A lid put back on is unlocked (`Vehicles.InstallComplete.Door`). Build 42 has no crowbar pry or lockpicking; a crowbar only pulls barricades and dismantles moveables.
- Opening a locked trunk tries its lock first (`ISVehicleMenu.onOpenDoor`, `Vehicles.Use.TrunkDoor`). The refused `ISUnlockVehicleDoor` stops, in single player from its `start()` and on a multiplayer client once the server rejects its `complete()` (`LuaTimedActionNew.update`), and that empties the queue before the open; its `stop()` tells the player why only for a broken lock. A broken lock (`VehicleDoor.setLockBroken`) makes `canLockDoor` and `canUnlockDoor` refuse; it is saved and sent with the door (`transmitPartDoor`), rides on the door's item while the part is off (`Vehicles.UninstallComplete.Door`, `InstallComplete.Door`), and `VehiclePart.repair` mends it.
- Opening a trunk picks its `TruckBed` container in the loot window only in single player: `ISOpenVehicleDoor.selectContainerInLootWindow` runs from `complete()`, which a multiplayer client never runs. Either way the loot window picks the first container when it goes from the floor alone to more (`ISInventoryPage.refreshBackpacks`), so a character alone at a trunk sees it anyway.
- The radial menu, the joypad prompt and a part's `use` reach a door only for a character inside its part's area and facing it (`BaseVehicle.getUseablePart`), so a character put in the middle of the area may be offered nothing.
- Vehicle zone stalls roll a vehicle at the zone's `spawnRate` (16% unless set) plus one, after `chanceToSpawnBurnt` and the 5% `chanceToSpawnSpecial` divert the stall, but `TrafficJamN/S/E/W` zones lay out their own slots and fill 81% of them (`IsoChunk.AddVehicles_TrafficJam_*`), and an `RTrafficJam` zone does so in a tenth of its chunks. The professions' `vehicle = "trades"` never spawns: nothing calls `RBBasic.doProfessionBuilding`.
- A dedicated server never creates `WorldSimulation`, so it runs no vehicle physics (`BaseVehicle.createPhysics`). A vehicle nobody drives moves only on a client that has taken `LocalCollide` authority over it; hitching through the server's `addPointConstraint` with a player gives it to that player's client, for car and trailer both. A trailer left alone on a server never settles.
- `addVehicleDebug` and the world's vehicle stories (`RandomizedWorldBase.addVehicle`, which falls back to the `junkyard` zone's vehicles) set every part's condition after the parts were made and their `create` Lua ran (`BaseVehicle.setGeneralPartCondition`), and the admin `/addvehicle` repairs the vehicle then (`AddVehicleCommand`), so a condition `create` gives a part doesn't survive them; zone spawns (`IsoChunk`) keep it.
- A hitch that snaps (see [Writing tests](#writing-tests)) breaks in the physics step that jolts it, and a multiplayer client has the server break it too (`BaseVehicle.breakConstraintOnServer`), so by the time Lua looks at the jolted trailer it is no longer towed.
- The server sends each client a vehicle's part changes (`transmitPartCondition`, `transmitPartItem`, model changes) every 100 ms, only while the vehicle is near that client, and clears them either way (`VehicleManager.sendVehicles`). A client that gets an update for a vehicle it doesn't have asks for the whole vehicle, and may ask twice; the server folds the part changes of that moment into the second full update, which a client that already has the vehicle reads only for its position (`VehicleFullUpdatePacket.parse`). So a change made within a few hundred milliseconds of a vehicle reaching a client can stay missing on that client until the part changes again.
- `vehicle:transmitPartModData(part)` sends the part's whole modData to the clients near the vehicle with its other part changes (`VehiclePartModData`); it does nothing outside a server. The part saves its modData with the vehicle, a container part's included.
- A vehicle's own modData has no way to the clients: `transmitModData` sends an object by its index among its square's objects (`IsoObject.transmitModData`, `writeToRemoteBuffer`), and a vehicle isn't one of them. Keep what clients must see in a part's modData and send it with `transmitPartModData`.
- Vanilla offers Remove Burnt Vehicle (welding mask and blowtorch) on any vehicle whose script name contains `Burnt` or `Smashed` (`ISVehicleMenu.FillMenuOutsideVehicle`). A smashed wreck's script copies its car's whole script (`template! = CarNormal`), so it has the car's parts, Engine and Battery among them; only the name tells it from the car. The scrap's `complete()`, on the authority, runs max(5, Metalworking) rounds of two rolls for each of its items, each roll a 1 in (the item's base − Metalworking, or for Engine Parts − the lower of Mechanics and Metalworking) to drop it on the vehicle's square (`checkAddItem`), and a server sends each drop to the clients itself (`IsoGridSquare.AddWorldInventoryItem`).
- The game lights a vehicle's mask zones from its `textureLights` texture, over the scene's lighting, in every frame it draws the vehicle (`BaseVehicle.updateLights`, from `render`): the headlights, stop lights and lightbar only with charge in a `Battery` part, but the window zones whenever `windowLightsOn` is set and the part of the window's id holds an item. `setWindowLightsOn` sets a plain field that nothing in the game sets or sends, so each game can flash a zone through it with no battery and no traffic. The zone colours are `vehicle_common.frag.h`'s `colZone` list; the enable arrays index `texen[a][b]` at `b * 4 + a`. `WindshieldRear` is index 14, the zone `(0, 127, 0)`: its part's condition dents it (`checkDamage`), rear blood stains it (`doBloodOverlayRear`), and rear crashes damage the part (`addDamageRear`).
- A lightbar or siren drains the battery only while the engine is off (`Vehicles.Update.Lightbar`, vanilla `Vehicles.lua`), so a battery update never both gains from the alternator and loses to the lightbar.
- `getCell():addLamppost(x, y, z, r, g, b, radius)` adds a light anywhere, in this game only, and `removeLamppost(light)` takes it away; each add or remove relights the cell (`IsoGridSquare.recalcLightTime`, `Core.dirtyGlobalLightsCount`), as vanilla's lightbar does on every flash (`BaseVehicle.updateWorldLights`).

## Art

- Build 42 draws tiles from 128 x 256 sprites (2x), in an orthographic projection 30 degrees above the horizon: a square's floor is a 128 x 64 diamond at the bottom of the cell, its centre at pixel (64, 224). A metre across the floor is 64√2 pixels, and a storey is 2.44949 metres, drawn 192 pixels tall (`TileDepthTexture`, `TileGeometryUtils`). The game's item icons are all 32 x 32 (in `UI.pack` and `UI2.pack`).
- A build-menu entry's icon is the `Icon` of its entity's xuiSkin entity style, which overrides the craftRecipe's own `icon` (`CraftRecipeComponentScript.getIconTexture`). It is looked up by the bare texture name (`XuiSkin` `Texture.trygetTexture`), where a recipe's `icon` gets `Item_` put in front (`CraftRecipe.OnScriptsLoaded`); a name that isn't found only warns in the log, and the entry falls back to the recipe's icon. The game's own build icons are 48 x 48 (`Build_*` in `UI2.pack`), which the menu scales to its tiles (`drawTextureScaledAspect`).
- A placed object given a sprite model (`setSpriteModelName`, a `spriteModel` script block) is drawn as that model, centred on its square, instead of its tile. The model camera scales everything by 1.5 and divides `translate` by it (`IsoObjectModelDrawer.renderMain`, `WorldModelCamera.Begin`), so a mesh in metres with model script `scale = 1` needs the sprite model's `scale = 0.6667`, as vanilla's doors have, to stand at its real size (checked in the art mode's `art_wind` shot). Without `texture` in the block the model draws white. A mesh exported by `art/models/models.py` is drawn half a turn round about the vertical from how it was built: its -Y side faces north at `rotate = 0 0 0` (art mode's `art_wind_tall`). A model over two storeys tall on a ground square draws whole beside the character, the cutaway notwithstanding (same shots).
- Since Build 42 each tile pixel is drawn at a depth read from a depth map. A mod's `common/media/depthmaps/DEPTH_<tileset>.png`, eight tiles wide like the tileset, loads only if the mod has a `common/media/tileGeometry.txt` (`TileDepthTextureManager.init`), which may hold no geometry; the game then logs that the mod overrides `media/tilegeometry.txt`, which is harmless, because the game reads its own by absolute path. A depth pixel is 1 − (east + south) / 4 − height / storey / 2, measured from the square's north-west floor corner in squares and storeys (`TileGeometryUtils.getNormalizedDepth`), and a sprite pixel whose depth pixel is transparent is not drawn at all (`tileWithDepth.frag`). A tile without a depth map is drawn as a box filling its square to the ceiling, unless it is a floor or a wall overlay (`IsoSprite.setupTileDepth`).
- The game reads depth maps by absolute path and refuses any path outside the mod folders, the cache dir and the game (`ZomboidFileSystem.validatePrefix`). It compares the paths without resolving symlinks, so a symlinked mod folder, or a cache dir under macOS's `/var`, which is `/private/var`, loses its depth maps.
- A wall-hung moveable has `MoveType = WallObject` and hangs on its own square: `Facing = S` with `attachedN` on the north wall, `Facing = E` with `attachedW` on the west wall (`ISMoveableSpriteProps.getWallForFacing`). `Noffset`, `Soffset`, `Eoffset` and `Woffset` give the tile number offsets of the other facings, which the placing cursor rotates through, and `CustomItem` names the item that picking the tile up gives.
- The placing cursor finds a facing's tile by adding that offset to the tile's number in the same tileset (`ISMoveableSpriteProps.getFaces`), so all of a moveable's facings must share a tileset. An offset must lie from -96 to 96: the game keeps only those values of the four offset properties (`IsoWorld.SetCustomPropertyValues`), and reads any other, such as 332, as -96, without a word. A mod's tileset holds at most 512 tiles (`IsoWorld.LoadTileDefinitions`); overlays may sit in any tileset. Turning a placed moveable in place picks it up and places it again (`ISMoveableSpriteProps.rotateMoveable`), which the cursor offers only while its container is empty (`canRotateMoveableInternal`), so a bank comes back as a new object.
- A vanilla treadmill's tiles (`recreational_sports_01_28` to `_39`) face away from the way a runner on it faces. Its console is the tile whose box in `media/tileGeometry.txt` stands about 1.2 to 1.4 up, which is also the one tile of the pair with `MaterialType = Plastic`. Its belt's top is 0.17 units (a level is 2.449) above the floor, so a character standing on the floor has their feet drawn inside the belt.
- A container holds at most 100 weight units, whatever its `ContainerCapacity` (`ItemContainer.MAX_CAPACITY`).
- The game draws a dropped item through the same 1.5 as a sprite model (`ItemModelRenderer$WorldModelCamera.Begin`, `Core.DoPushIsoStuff` with `vehicle` false), so a ground model exported from Blender in metres with HearingAid's FBX settings needs `scale = 0.6667` in its model script to lie at its real size; at `scale = 1` it lies half again too big. The game's own items aren't all life size: its car battery mesh at `scale = 0.4` is 0.19 x 0.13 x 0.14 m (a 0.48 x 0.33 x 0.35 mesh), drawn at 1.5 times that, a little over a real one, so a life-size battery looks too small beside it. A Moveable with a `WorldStaticModel` lies on the floor as that model (`IsoWorldInventoryObject.render`, `ItemModelRenderer.itemHasModel`); vanilla's drums have none and lie as their flat icon.
- The game lights each face of a world item about evenly and darkens dark colours towards black: in the promo's item shots a texture's (33, 85, 168) comes out (0, 16, 46), and the game's own car battery's #3f3f3f sides nearly black. A model in one colour so draws as a flat patch with its edges lost, which is why `art/models/models.py` paints the light into ground models' textures (`paint_light`), and why the car battery case is a lighter grey than the game's battery.
- The closest zoom the game draws is 25% (`MultiTextureFBO2.zoomLevelsDefault`), but the default zoom options stop at 50%. `getCore():setOptionZoomLevels2x(levels)` (`1x` for 1x tiles) and then `getCore():zoomLevelsChanged()` change the levels in a running game without saving them.
- `faceDirection` turns a character over about half a second; `setTargetAndCurrentDirection(x, y)` turns it and its animation at once. What it sees follows on the lighting thread, which runs `lightFPS` passes a second (15 by default; `PerformanceSettings.lightingFps`), so a square it never saw stays dark until a pass or two after it faces that way. Raising it spoils screenshots: at 60 night came out lighter and walls half see-through, and at 120 the thread falls behind and leaves squares dark.
- A lamp from `getCell():addLamppost(x, y, z, r, g, b, radius)` lights only the game that adds it, and the native lighting doubles its colour and clips it at 1 (`LightingJNI.checkLights`), so pass half the colour: given whole, a warm white shines pure white. A lamp's `setR`, `setG` and `setB` recolour it at the next lighting pass, as vanilla does when a lamp's bulb changes (`IsoLightSwitch.setPrimaryR`); `removeLamppost(lamp)` drops it at that pass too, and `getLightSourceAt` finds it until then.
- `getClimateManager():stopWeatherAndThunder()` leaves fog and cloud to fade out over seconds; setting the admin value of the climate floats `FLOAT_FOG_INTENSITY`, `FLOAT_CLOUD_INTENSITY` and `FLOAT_PRECIPITATION_INTENSITY` to 0 clears them at once. A fresh world rolls its weather, and burns some houses, anew every run.
- Game wind (`getWindspeedKph`, the climate's wind power × 120) outside a weather period's windy stages is the climate's base wind, up to about 78 km/h when the air mass is cold and the days short (`ClimateValues` `windBase`), so drizzle or moderate rain can blow harder than heavy rain, which tops out at 60. A thunderstorm stage blows 24 to 84 km/h, a blizzard 90 to 120 for 24 to 48 hours, a tropical storm 48 to 120 (`WeatherPeriod.updateCurrentStage`, `createStage`). `getIsThunderStorming()` is true through a tropical storm too, and false through a blizzard.
- A square's `WallN`/`WallW` flags don't mean a solid wall: tall wooden fences (`fencing_01_8`, `TallHoppableN` with `WallN`) and low house walls (`walls_exterior_house_low_01_*`, `HoppableN` with `WallN`) carry them too, while window and door frames carry `WindowN`/`WindowW` and `DoorWallN`/`DoorWallW` instead, and see-through fences `WallNTrans`/`WallWTrans` (`newtiledefinitions.tiles`). Vanilla tells fences apart by the `Hoppable` and `TallHoppable` flags beside its wall checks (`IsoGridSquare`).
- The UI draws at its own rate, the `uiRenderFPS` option (at most 120; `Core.StartFrameUI`), and the frames in between show its last drawing, so at an uncapped frame rate a count of frames can pass with no UI drawn. `getCore():setOptionUIRenderFPS(n)` changes it in a running game; the game saves its options at times, so put the old rate back before the game quits.
- A vehicle body's damage, blood, rust and lights come from textures and a mask in its skin's UV space. Of the stock vehicle shaders only the multi-UV family (`vehicle_multiuv*`) draws blood, and it samples rust, damage and blood through a second UV layer, so the mesh needs a copy of UV1 as UV2; without it they sample one texel. A shader name ending in `_noreflect` keeps sky reflections off whatever the reflections option says.
- The damage shells draw their own colour on Head, Tail, windows and lamps, at full alpha. Everywhere else they take the paint's hue, add their saturation and value to the paint's minus a half, and draw at three quarters of their alpha (`vehicle_common.frag` `addDamage`). The paint is the skin texel under `vehicle_norandom_*`, so dents on a saturated paint keep its colour; under `vehicle_multiuv*` it is the vehicle's colour, and a `forcedColor` of half saturation and value leaves a grey shell grey. A skin texel with alpha below 1 is repainted in that colour, so an opaque skin never is.
- The mask's colours pick zones, matched within 0.01 and filtered linearly, so a seam between two zones whose blend passes through a third lights a line of that one. Head takes Front blood, Tail and Boot Rear, Guard LT and RT Left and Right (the single-UV shaders swap the guard colours), and the StopLights zones light while the towing car brakes, for any vehicle script whose name contains `Trailer`. White matches no zone, so it never takes blood or damage.
- Damage stage 1 is a part condition of 40 to 59 and stage 2 below 40 (`BaseVehicle.doDamageOverlay`). Rust is not gated by the mask, so its own alpha keeps it off the panels and lamps. Rust is rolled once at spawn, and `repair()` clears rust and blood.
- In multi-UV shaders `textureDamage1Overlay` is blood's growth mask (alpha: where blood shows first as a side's intensity rises) and `textureDamage2Overlay` its colour; they are not damage overlays.

## Loot

`IsoWorld.init` fires `OnDistributionMerge` and `OnPostDistributionMerge`, then loads the save's sandbox options, then calls `ItemPickerJava.Parse()`, then fires `OnInitGlobalModData`. When a single player game is continued, the merge events therefore see the sandbox options of the default preset. Loot that depends on sandbox options has to be added in `OnInitGlobalModData`, followed by another `ItemPickerJava.Parse()`.

- The chance per roll is ⌈weight × 100 × loot category multiplier + zombie density bonus⌉ in 10,000, and a container rolls `rolls` times (`ItemPickerJava.getActualSpawnChance`). Every positive chance rounds up to at least 1 in 10,000, so at the default multiplier of 0.6 a weight below 1/60 spawns more often than it says. The multiplier is a float a little above 0.6, so a product that should come out whole rounds up too: a weight of 0.25 gives 16 in 10,000. The density bonus is added, not multiplied, so it's the same for every entry whatever its weight. The Lucky and Unlucky traits don't affect loot.
- `items` lists are flat name and weight pairs, so always append both. Unknown item names are dropped, with a message only in debug logs.
- `junk` lists roll with the loot category multiplier fixed at 1.0 and weights × 1.4, so the loot rarity settings don't scale them. They are often shared by reference (`ClutterTables.*`), so don't add to them.
- A corpse rolls its loot when it's first opened or its square first loads: `SuburbsDistributions.all.Outfit_<outfit>`, and then `inventorymale` or `inventoryfemale` unless the outfit table sets `defaultInventoryLoot = false`. The comment in vanilla `Distributions.lua` that says outfit tables replace the gendered ones is wrong.
- `ItemPickerJava.fillContainer(container, nil)` works without a player, as loot respawn does. A container marked explored is never filled again, so fill one before `setExplored(true)`.
- Loot respawn refills any explored container below `MaxItemsForLootRespawn` in a town or trailer park zone, generators' containers included (`LootRespawn.respawnInContainer`). Give a container type that players stock an empty loot table.
- `ZombRand(min, max)` never returns `max`.
- Outside shops, 40% of the items a room or corpse rolls that show their condition (the `ShowCondition` tag, weapons, sharp tools) get a uniform condition from 1 to the maximum before `OnFillContainer` fires (`ItemPickerJava.doRollItemInternal`, `randomizeGeneralCondition`), and every such item rolled into a bag does (`rollContainerItemInternal`); shop stock and anything Lua adds come at full condition. A test of found wear can't force that roll.
- `ItemContainer.AddItem` puts every new item on the cell's processed items (`IsoCell.addToProcessItems`), an `ArrayList` it scans on every add, and the cell drops an item only on a later frame. Filling scratch containers thousands of times in one frame piles them up until the game crawls and runs out of memory, so take each sample's items off `getCell():getProcessItems()` yourself.
- `ItemPickerJava.updateOverlaySprite(object)` sets a container's few-items or full overlay. On a server the overlay goes out by the object's index on its square, so call it only after clients have the object.
- The map zones loot and Lua read with `getZonesAt` (`TownZone`, `TrailerPark`, `Farm`, the forests) come from Build 42's biome map (`media/maps/<map>/maps/biomemap_<x>_<y>.png`, `BiomeMapConfig.lua`) and exist only once their cell has loaded; a far square has only its `Region` zone. The map's `objects.lua` doesn't match them. Most farmhouses sit in `TownZone` there, and `Farm` marks fields.
- The map's barns hold almost no loot containers: across its 201 barn rooms there are 56 crates and shelves besides 1,550 feed troughs (`dev/loot/census.py`), and most of those pick `CrateAnimalFeed`. Loot weights in `BarnTools` hardly reach a player; story clutter on barn tables (`RBBarn`, always run) and things Lua leaves in the building do.
- `StoryTables.addItemToClutterTable` adds every item to a clutter list twice, vanilla's own included, so relative weights hold but a list's count of an item is twice the adds.
- The `--loot` report's room estimates leave out lists a room only rolls for certain tiles, rooms or zones (`forceForTiles` and the like), such as the hardware store's book shelves, so it undercounts what stores' magazine racks give.

## Workshop page

- The in-game Workshop screen uploads `Contents/` and `preview.png`; the other files at the repository root aren't uploaded. `dev/harness/docs/workshop-page.md` has the Workshop's limits.
- Steam shows the preview as small as about 196 pixels. In the game's mod list, `mod.info`'s `icon=` is drawn about 22 pixels square (the small font's height plus a little; `ModListBox`) and 28 in the load order, through `getTexture`, which loads it with linear filtering and no mipmaps, so a picture larger than about twice that size is sampled past its thin lines. `mod.info` takes one `category=`, which the mod list's filter matches exactly; the first `poster=` is the main poster.

## Save compatibility

Code kept only so older saves load, to delete once they needn't:

- `Sprites.fixedTiles` and everything that reads it (`Sprites.turnable`, the `KINDS` copy in `Sprites.lua`, `PowerBank.lua`'s bank sprites, the `instanceItem` and `placeMoveableInternal` wraps in `Moveables.lua`, `RenewableEnergyTestsTiles.lua`'s fixed-tile test and `RenewableEnergyTestLib.lua`'s list), and the old tiles in the tileset: renewable_energy_01_8, 9, 23, 32, 33, 34, 244 and 245. Banks and heaters placed before they turned (commit 811e5f6) stand on those tiles. The engine finds a tile's other facings at most 96 tile numbers away (`IsoWorld.SetCustomPropertyValues`), and none are free near them, so they can't turn; the code treats them as their turnable twins.
- `WindSource.lua`'s `bladesOf` falling back to `Wind.bladesOf(source.kind)`: a bank's record of a wind charger connected before records kept their blades has none until the charger's chunk loads.
